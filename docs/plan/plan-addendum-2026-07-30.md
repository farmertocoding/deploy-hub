## A. Decisions resolved this round (research-backed — no longer open)

**A1. Hub auth = Django session cookies, not JWT.** HttpOnly/Secure/SameSite=Lax session cookie + DRF SessionAuthentication + CSRF token header for the SPA. JWT in browser storage is XSS-exfiltratable and effectively unrevocable, which would break the §6.10 step-up guarantees. WebSocket: Channels `AuthMiddlewareStack` rides the same session; reject unauthenticated at connect; every topic subscription passes one `authorize_topic(user, topic)` function — a single testable choke point. Step-up mechanism pinned: hardware re-auth writes a server-side `hardware_touch_at` timestamp into the session; dangerous-action endpoints check it via one `require_recent_touch(minutes=5)` DRF permission class. Session TTLs (from CircleCI lesson, §B6): idle timeout ~30 min, absolute ~12 h.

**A2. YubiOTP/YubiCloud dropped; WebAuthn primary, TOTP fallback.** Research verdict: YubiCloud still operates but is in maintenance mode — Yubico archived all legacy validation client libraries ("will not be updated"), retitled its YubiCloud guides "[deprecated]", and omits the OTP application from its current Security Key line. Implementing YubiOTP would add a third-party cloud call into a self-hosted auth path for a mechanism the vendor is de-emphasizing, and duplicates nothing WebAuthn doesn't do better (phishing-resistant, origin-bound, fully offline on the LAN). **Your YubiKeys stay the centerpiece — as WebAuthn security keys** (`django-otp-webauthn`), with TOTP as the explicitly-chosen fallback. This removes `django-otp-yubikey` from the stack.

**A3. KEK default = cloud KMS (AWS KMS).** ~$1/month + $0.03/10k requests (20k/month free); 99.999 % regional SLA; KEK provably never on any disk you own; CloudTrail gives KEK-usage audit logs free. The unlock path only gates *restarts* — DEKs already unwrapped stay cached in worker memory, so a KMS blip never stops serving. Decisive argument: CircleCI's attacker "extracted encryption keys from a running process" — a keyfile on the Hub host (old option ①) is defeated by exactly the live-compromise scenario the plan worries about most. Ladder now: **③ KMS = default for any Hub holding real fleet credentials; ② YubiKey challenge-response = offline homelab option (physical touch at service start); ① keyfile = dev/test only.** Break-glass: passphrase-encrypted KEK copy on paper/password-manager, offline, to survive cloud-account loss. Boot path degrades gracefully (retry with backoff; keep serving from cached DEKs). Phase 5+ upgrade if the fleet grows: **OpenBao** (not HashiCorp Vault — BUSL; OpenBao is production-ready since v2.0/2024, OpenSSF sandbox, adopted by Nvidia/SAP), Transit engine as KEK service, cloud-KMS auto-unseal.

**A4. Canonical deploy source = git URL/branch cloned by the Hub.** The master plan's "select a path" had no defined path from laptop to an isolated Hub (critical product finding — the first real deploy from a properly-isolated Hub was impossible as written). Decision: the Hub clones a git URL + branch (GitHub private repo or a bare repo on any reachable host); scans run against a *commit*, making readiness reports reproducible; this also makes branch deploys and webhook auto-deploy (§E1) nearly free. Local-path mode survives as a dev convenience only while Hub and code share a machine, boundary stated in the UI.

**A5. Locks = Postgres, not Redis.** P3's whole correctness story rested on Redis locks — but Redis is also broker + channel layer, isn't persistent by default, and a Redis restart mid-deploy would vaporize the lock and let a second operation interleave (the exact corruption P3 exists to prevent). Locks move to Postgres (lock table; Postgres is already the source of truth and survives what Redis doesn't). Redis stays broker/channel-layer/cache only; its loss = "tasks re-enqueue, panels re-snapshot," never corruption.

**A6. Paging channel = ntfy (hosted ntfy.sh), email for digests.** Email cannot wake anyone; a solo operator needs exactly two delivery classes (see §C5). ntfy is free, trivially callable from Celery, and self-hostable later if wanted. (Pushover is the $5 fallback if ntfy proves unreliable in practice.)

**A7. Test stack pinned** (full harness in `build-process.md`): pytest everywhere · unit seam = the command catalog itself + a narrow `Transport` interface with Fake/Recording implementations + Fabric's first-party `fabric.testing` doubles · AWS = moto 5.x `@mock_aws` (**not LocalStack** — its anonymous free tier ends 2026-03-23 and became non-commercial-only) · Azure = own `CloudProvider` port + in-memory fake, thin adapter tested via the SDK's official `transport=` injection · integration targets = testcontainers-python + a custom `hub-test-target` image (Ubuntu + sshd + systemd + inner dockerd) · full-fidelity e2e = real Ubuntu VM — **Multipass** locally (not BSL-licensed Vagrant), QEMU/cloud-init on GitHub Actions (free runners have /dev/kvm since Apr 2024) · fault injection = **toxiproxy** on the SSH path (timeout mid-deploy → assert resume) · UI e2e = **Playwright** + pytest-django `live_server`, with **Chromium's WebAuthn virtual authenticator** so mandatory 2FA and automated testing stop being in conflict.

**A8. Frontend component stack = shadcn/ui + Tailwind.** Chosen for first-class react-hook-form + zod fit (§4.5 already mandates both), built-in dark-mode tokens (this tool is used at night), accessible primitives, and copy-in components that match mockup-first. Map library still open (§J) — settle by prototyping the 30-node worst case, not feature lists.

**Still open (parked with owners in §J):** container-vs-VM fidelity spike for the integration tier; exact SSH-CA vs scheduled-rotation design (§B7); map library; tailnet-lock adoption timing.

## B. Security — adopted fixes

**B1. Builds move off the Hub (critical).** `docker build` executes arbitrary project code (RUN steps, pip/npm postinstall) with network access against a root-equivalent daemon; running it on the Hub violates the plan's own top rule (§9.6.2 r1) and hands a malicious lockfile dependency the keys to the fleet. **Builds run on the deployment target itself** (build context shipped over SSH; the target is already in its own site's blast radius). A dedicated cheap builder target is the later upgrade; rootless BuildKit with `--network=none` post-fetch is the only sanctioned interim if a target build is impossible. Env files and vault material are injected at deploy time only — never present in any build context. Generated Dockerfiles: `npm ci` (never `npm install`), `pip install --require-hashes` when the lockfile has hashes; scanner offers `pip-compile --generate-hashes` as a fix-it and warns on any `--extra-index-url`/custom registry config (dependency-confusion vector).

**B2. No DNS tokens on targets (critical-adjacent).** Caddy-does-DNS-01 would put a *zone-scoped* Cloudflare token on every target; Cloudflare tokens can't scope to a record, so one compromised host could repoint any site in the zone. New cert architecture: proxied sites → **Cloudflare Origin Certificates** (15-year, free, zero renewal machinery) pushed via the §7.4 uploaded path; unproxied sites → Hub-central DNS-01, cert pushed to Caddy, renewal owned by a Hub Beat job with the §6C expiry watch as the safety net. P2 note: a pushed cert lives on the target's disk, so sites keep serving with the Hub down; only *renewal* is Hub-dependent, and the 45/21/7-day alerts catch a dead renewal path long before expiry.

**B3. Audit trail ships off-host, append-only (critical).** The §6.8 worst case ("attacker owns the Hub → full audit trail for forensics") was self-referential — the trail lived in the DB the attacker owns. Now: one `AuditEvent` model (schema in §D1) + near-real-time shipping to an S3 bucket with **Object Lock (compliance mode, 90-day retention)** under an IAM key that can *only* `s3:PutObject` — no read, no delete — plus a per-row hash chain (`hash(prev_hash + row)`) so local tampering is detectable. One Beat job + one bucket policy.

**B4. Redis is inside the crown-jewel boundary.** Whoever can write the Celery broker can enqueue tasks that run root commands fleet-wide. Phase 0 config, non-negotiable: Redis on the compose-internal network only (never a published port), `requirepass` generated, Celery serializers pinned to JSON (never pickle), and "Redis unreachable from outside the Hub host" added to the §6B external port-scan of the Hub itself.

**B5. Cloudflare token discipline (the plan's most powerful credential had no rules).** Never the Global API Key. Two scoped tokens in the vault: DNS ops (`Zone:DNS:Edit`, restricted to the specific zones) and attack playbook (`Zone:Firewall Services:Edit` + `Zone Settings:Edit`), IP-filtered to the Hub's egress where static. A §6B audit check calls `/user/tokens/verify` and alerts if configured scopes exceed the minimum. Similarly: the `cloudflared` tunnel credential is acknowledged in the §6.8 table as a target-held secret — one tunnel per target, revoked on decommission.

**B6. Threat model gains three rows (incident research).**
- **Stolen live session / laptop malware** (CircleCI 2023: MFA was bypassed because the login had already happened). Mitigations: the A1 session TTLs; step-up hardware touch on secret decrypt/export, target delete, KEK ops, auto-mode changes — now **mandatory, not optional**; session bound to Tailscale device identity where feasible (custom middleware; verify feasibility during Phase 4).
- **Operator workstation** (NIST 800-204D: "developer workstations present a fundamental risk" — the laptop *is* the access point). In scope now: full-disk encryption on the laptop, no long-lived Hub credentials cached, short sessions, OS auto-update discipline. Solo substitute for the two-person rule: hardware step-up + time-boxed privileged mode.
- **Silent long-dwell tampering** (Codecov: 2 months undetected; found by an external checksum). The §6.8 anomaly alerts (mass key access, off-hours deploys, backup-bucket access) are re-classified **load-bearing**; every artifact the Hub pushes (env files, scripts, certs) is checksum-verified after write on the target; the Hub's Django/DRF dependency security releases are monitored (a Beat job checks PyPI advisories) so the self-built control plane gets patched as fast as a vendor's would — TeamCity's CVE-2024-27198 validated Tailscale-only isolation as the backstop that makes an app-layer auth bug survivable; it stays non-negotiable.

**B7. SSH credential longevity.** CISA/NSA prescribe ephemeral SSH access; long-lived vault keys are the current design. Adopted in two steps: **now** — §7.4 rotation becomes *scheduled* (quarterly, automated via the existing rotation playbook) instead of on-demand-only; **Phase 5 research item** — an in-Hub SSH CA issuing short-TTL certificates per deploy (design decision parked, §J).

**B8. Tailscale account = unmodeled SPOF, fixed.** The tailnet is the trust anchor for four defenses, and it authenticates via an SSO account the plan never secured. Adopted: hardware-key 2FA on the SSO account that owns the tailnet; **tailnet lock** evaluated in Phase 4 (verify current UX first — it adds signing ceremony to the 2-minute enrollment flow); a Beat job polls the Tailscale API device list and alerts on any device/auth-key the Hub didn't create. New §6.8 row.

**B9. Test credential plane is separate by construction.** The live-test harness gets: a dedicated AWS member account / Azure subscription with its own budget alarm ($10) and no path to prod resources; the dedicated test DNS zone with a zone-scoped token; per-test-run generated SSH keypairs destroyed with the target; the §9.5.5 reaper extended to `purpose:test` tags; a `HUB_TEST_MODE` settings flag that *refuses* to touch any non-test zone. Prod vault credentials never enter the harness.

**B10. Small adopted items:** SSRF guard in the §4.5 domain/URL validators (reject/warn on private ranges, 100.64/10, localhost, 169.254.169.254) · Hub's own Django hygiene stated (/admin disabled or Tailscale-IP-bound + 2FA, browsable API off, the Hub passes its own §5 scanner) · Caddy admin API stays on localhost, reached only through the existing SSH channel · break-glass runbooks are 0400 root-owned and never contain secrets · Tailscale bootstrap pins the install (distro package preferred over curl|sh), pre-auth keys get short expiry + revocation after enrollment · log-scrubber scope extended to SSH transcripts and WebSocket-streamed deploy logs · no internal HTTP calls between Celery and the API (tasks call service functions directly; one less credential class to exist).

## C. Reliability — adopted fixes

**C1. Deployment liveness + orphan sweep.** Running pipeline tasks update a `last_heartbeat` column every ~30 s; a boot-time and periodic sweep resumes-or-aborts any `running` Deployment whose heartbeat is > 2 min old. (P3 promised resume; this is the thing that *notices* death.)

**C2. Reconciler brakes** (the biggest gap in the plan's own biggest upgrade): ① `maintenance_until` per site/host — one click; reconciler observes and reports but never acts while set; auto-expires (stops it fighting you mid-debug at 2 a.m.); ② per-resource exponential backoff — after 3 failed convergences of the same diff, stop, alert once, require manual re-arm (no infinite crashloop-restart); flap detection: same resource "fixed" > N times/hour → "something is fighting the reconciler" alert + pause; ③ global convergence budget with jitter — after Hub downtime it catches up over 15–30 min, not one stampede into Cloudflare rate limits; ④ re-probe + lock re-check immediately before any mutation (never act on stale observation); ⑤ kill-switch — global `reconcile_enabled` + per-site pause, in the UI, step-up-gated. Intervals per resource type: containers/Caddy 60–120 s · DNS 10–15 min · hardening drift daily · certs daily. Every repair writes an AuditEvent.

**C3. One collector session per target per minute.** As written, each target got 3–4 separate SSH connections per minute (metrics, logs, reconciler probes) — enough to trip the plan's *own* `ufw limit 22` rule and ban the Hub from its fleet. Now: one SSH session per target per minute runs one small script returning JSON (metrics + container states + log chunk with next offset + clock sample), with per-target jitter (`hash(target_id) mod 60`). The Hub's mesh IP is whitelisted from fail2ban/ufw-limit in the catalog. The collector JSON contract is a Phase-2 pinned interface — monitoring, reconciler, and ingest all ride it.

**C4. Log pipeline gets backpressure + rotation.** Caddy log rotation (roll_size 100 MB, keep 5) becomes a provisioner catalog entry — target disk is bounded no matter what the Hub does (an unrotated log during a spike + Hub outage = attacker fills the disk via the monitoring system). Per-pull byte cap with degrade mode: over the cap, an on-host one-liner aggregates counts by status/IP and the Hub ingests the summary flagged "sampled" — the attack detector needs counts and concentration, not every line. Offset tracking pinned: per-file inode + offset on the Target row.

**C5. Alert policy (solo-operator honest).** Two channels only. **PAGE (ntfy push, repeats hourly until acked):** prod site hard-down > 5 min · Hub DB/backup failure · attack playbook engaged · budget cap hit · dead-man's switch. **DIGEST (daily email):** everything else. Root-cause suppression (host-down suppresses its sites; zone-down suppresses its hosts — generalizing the existing zone logic); hysteresis (open after 3 consecutive failures, close after 2 successes; flapping collapses to one "flapping" alert). One email template: subject `[Hub P1] mysite.com DOWN 4 min`; body = what/where/since-when/current-status/one-action + deep link; always send the recovery notice. Alert emails are self-sufficient (inline break-glass command where relevant) because "Hub unreachable" is precisely when some of them fire. Uptime-probe vantage caveat: before declaring mass outage, probe a known-good canary; if it also fails, alert "Hub egress degraded" instead of N pages. **UPDATE 2026-08-02 (review3 §V8):** alert-protocol.md's three-behavior model (P1 page / P2 push / P3 digest) formally amends the "two delivery classes" wording above; alert-protocol.md §2 is the operational authority.

**C6. The Hub's own upgrade runbook** (who deploys the deployer): `hub-upgrade.sh` — check/wait for no running Deployment, `pg_dump`, pull + build, migrate (the §8.3 expand-contract rule applies to the Hub's own schema too), warm-shutdown Celery restart (SIGTERM, tasks checkpoint), smoke-test login + one probe cycle, previous image kept for one-command rollback. Half a day; written in Phase 2.

**C7. Housekeeping adopted:** Beat singleton guards (skip-if-running via Postgres lock row; startup advisory lock prevents a stray second Beat double-firing everything) · dead-man heartbeat emitted at the *end of a real probe cycle* so it proves scheduler + broker + worker + SSH end-to-end, not just that Beat ticks · NTP (chrony) added to the provisioning catalog + a clock-skew probe in the collector (finding > 2 s, alert > 30 s — skewed clocks silently corrupt the attack-detector baselines) · retention janitor with pinned numbers: HostMetric raw 14 d/hourly rollup 1 y · UptimeEvent 90 d/daily rollup forever · TrafficStat minute 48 h/hour 90 d/day forever · deploy logs to gzip files after 30 d · AuditEvent forever (it's small). Plain nightly batched DELETEs; no partitioning, no TimescaleDB at this scale.

## D. Architecture — pinned specifications

**D1. AuditEvent model (was load-bearing in six sections, modeled in none):** `AuditEvent(id, ts, actor FK User nullable, source: ui|api|celery|reconciler|system, action slug, object_type, object_id, target FK nullable, detail JSON, source_ip nullable, severity: info|warning|security)` — append-only, written via one `audit(action, obj=None, **detail)` helper (if emitting isn't one line, coverage rots), indexed on (ts) and (object_type, object_id), shipped per §B3. Anomaly alerts and the §4.5 fail2ban feed are queries over this table.

**D2. Deployment state machine, finally enumerated:** `Deployment.status ∈ {queued, running, succeeded, failed, rolled_back, cancelled, superseded}` · `DeploymentStep(deployment FK, seq, name ∈ [build, ship, migrate, start_green, health_check, dns, route_tls, smoke_test, cutover], status ∈ {pending, running, succeeded, failed, skipped}, started, finished, log_text, artifacts JSON)` · text artifacts inline in `DeploymentArtifact(deployment, kind, content TEXT)` (kilobytes; object storage is premature) · images referenced by tag+digest only. **Env snapshots go through the vault code path** — stored as EncryptedField ciphertext with AAD bound to the deployment id (the naive P4 reading would have copied vault contents into every Deployment row, silently defeating §6.9). Resume = first non-succeeded step. Rollback = a *new* Deployment row referencing the target deployment (history stays append-only). A new deploy while one runs marks the old `superseded` at the lock boundary.

**D3. Desired state is relational — the JSON blob is dropped.** `SiteInstance` gains `desired_image_tag, desired_state ∈ {running, stopped, absent}, observed_state, observed_at, last_reconciled_at, consecutive_failures`; `DnsRecord` rows *are* the desired records (+ `observed_value, last_verified`); the Caddy route is derived by a pure `render_caddy_route(site)` function. The reconciler reads models, never JSON — one source of truth, per P4's own rule. Per-site Caddy overrides (rate limits, body caps) live in a small versioned pydantic-validated config field; the reconciled facts stay in columns.

**D4. Django app layout (module boundaries made structural):** `hub/` (settings, celery, asgi) · `core/` (zones, targets, projects, sites, instances, AuditEvent) · `vault/` · `catalog/` · `scanner/` · `provision/` · `deploys/` (models + `steps.py` ensure_* functions + pipeline task) · `reconcile/` (imports deploys.steps — pipeline and reconciler share the same primitives) · `providers/` (base interfaces + cloudflare/route53/azure_dns/ec2/azure_vm + `fakes.py`) · `monitor/` · `scaling/` · `realtime/`. One hard rule enforced by a 10-line import-grep test: **boto3/azure-*/Cloudflare clients import only under `providers/`**. This is what makes "Phase 5 is only provisioning + DNS code" verifiable instead of aspirational, and what the test fakes plug into. **UPDATE 2026-08-02 (review3 §V6):** the module seam's home is pinned — `scanner/modules/<name>.py` + `scanner/core.py`; the wizard **materializes `dockerfile_template` (and all module outputs) into the stored deployment manifest** — `deploys/` reads only the manifest, never imports scanner.

**D5. Provider interfaces pinned before any implementation:** `DnsProvider`: `list_records(zone)`, `upsert_record(zone, name, rtype, values, *, proxied=False, ttl=None)`, `delete_record(zone, id)`, `get_nameservers(domain)`, `capabilities() -> set`. **`EdgeProtection` is a separate interface** (`set_security_level`, `ban_ip`, `purge_cache`) implemented *only* by Cloudflare — the §6.5 L5 playbook takes `EdgeProtection | None` and degrades to notify-only explicitly, in code, so Route 53 in Phase 5 can never silently no-op a security action. `CloudProvider`: `create_instance(spec)` (returns provider-fetched host keys for §6.8 pinning), `get_instance`, `terminate_instance` (idempotent; already-absent == success — the reaper depends on it), `ensure_ingress_rules` (declarative, for §6B parity audits), `list_tagged_instances`, `create_image`, `estimate_hourly_cost`.

**D6. Idempotency written per step, not asserted:** every pipeline step is `ensure_X(desired)` — probe observed, act on diff — in `deploys/steps.py`, shared verbatim with the reconciler. Per-step rules: build → tag = f(git sha + manifest hash), exists = skip · ship → `docker image inspect` first · migrate → Django's migration table makes it re-runnable; backup guarded by the step record (crashed mid-step = fresh backup; extra backup harmless, missing one is not) · start_green → deterministic name `site-{slug}-{deployment_id}`; exists+healthy = adopt, exists+dead = recreate · dns → list-then-diff upsert keyed (name, rtype) · caddy → route carries `@id site-{slug}`, PUT-by-id (also lets the reconciler distinguish "route missing" from "route hand-edited" — repair vs alert, never clobber) · cutover → grace deadline persisted on the step row. Standing test rule: every step and playbook runs twice in tests; second run must record **zero mutating Transport calls**. **UPDATE 2026-08-02 (review3 §N1/§N5):** volumes are per-**Site** (`site-{slug}-data`), never per-deployment; created by an idempotent `ensure_volume` primitive shared by pipeline and reconciler; never touched by rollback, the reaper, or decommission without a T1-tier confirmation.

**D7. Realtime contract (~40 lines, written once in Phase 0):** one `EventsConsumer` (session-authenticated in `connect()`, reject anonymous); client protocol `{action: subscribe|unsubscribe, topics: [...]}`; topic string = Channels group name verbatim (validator enforces the allowed charset); `publish(topic, event)` does `seq = redis.incr(f'evt:seq:{topic}')` then `group_send` — one INCR, nothing else stored; every snapshot REST endpoint returns `{seq, data}` from the same key; client discards events with `seq <= snapshot.seq` and treats any gap/regression as "refetch snapshot." Blue-green port allocator: per-target range 20000–29999, recorded on SiteInstance, uniqueness by DB constraint.

**D8. Catalog lifecycle:** entries get a stable id + integer version (changed semantics = version bump, never silent mutation; rollback commands retained per version); `AppliedCatalogEntry(target, entry_id, version, applied_at, mode, result)` written on every execution. Drift audit then distinguishes "observed ≠ applied version" (real drift → re-apply) from "applied < current" (upgrade available → show delta commands). Catalog format decision: **Python dataclasses** (`catalog/entries.py`), not YAML — type-checking, comments, per-OS variants free. `scan_report` and `CheckRun.results` JSON get `schema_version` from day one (they're diffed across runs; unversioned shape changes are the first silent breakage a refactor causes).

**D9. Canonical vocabulary (frozen into table names, API fields, UI copy):** **Project** = code (git URL/branch) · **Site** = project + domain + config · **Instance** = one running copy of a Site on one Target (SiteInstance) · **Target** = a managed host, permanent or ephemeral — never called an "instance" in UI copy · **Zone** = a network · **Deploy** = the act/record. `ScalePolicy.max_instances` documented as counting SiteInstances. Auth models: Django's built-in User (one row) + django-otp device tables; `triggered_by`/`actor` are FKs, not free text.

## E. Product scope — adopted additions

**E1. Webhook/push-triggered deploys move from Phase 7 to Phase 2.** Research (primary docs): all five reference tools — Coolify, Dokploy, CapRover, Portainer, Dokku — ship push/webhook-triggered git deploys; it is *the* baseline interaction model. One authenticated per-site webhook endpoint enqueuing the existing deploy task + per-branch config. Full GitHub-App integration stays later. **UPDATE 2026-08-02 (review3 §M2):** the transport changes — Phase 2 ships git **polling** (a Beat job checks each site's branch head every 1–5 min), **not** a webhook endpoint, preserving the zero-inbound invariant (§K1/R1); true webhooks arrive later as a credential-free outbox message type on the Phase-5.5 intake, pulled by the Hub like partner jobs. The research conclusion (push-triggered deploys are the baseline interaction) stands; only the transport changes.

**E2. Deployment history with one-click rollback to any version** (Coolify/Dokploy/CapRover pattern): Deployments list per site, each row Rollback-able via the existing cutover machinery; depth limited by kept images now, unlimited once registry shipping lands (schedule the registry no later than Phase 5 — all five tools converge on registry distribution for multi-server). Registry security spec, when it lands: TLS + auth required, push rights limited to the build path's credential only (a push-open registry is a supply-chain injection point into every subsequent deploy), pull via per-target read-only credentials.

**E3. App-log viewer (conspicuously absent — every mature PaaS has it).** Per-site Logs tab, Phase 3: `docker logs --follow` over the existing SSH transport → `site.{id}.applog` topic on the already-built socket. Table-stakes UI from Portainer's spec: search with hit navigation, tail-N, timestamps toggle, wrap, copy, download. Persist/search stays out of scope (Sentry covers exceptions); live tail + last-N is the need.

**E4. Env-var lifecycle** (would have bitten in week one): per-site Environment page — names listed, secret values masked/write-only, add/edit/delete marks the site **config-stale** with one-click Apply = pipeline steps 4–9 with the existing image (a "restart with new env, same image" variant that cert-mode switches and Caddy-route changes also reuse). Env bundles are already P4 artifacts, so running-vs-desired env diff falls out free.

**E5. DB lifecycle gets an owner.** The wizard asked "which DB?" and nobody provisioned it. Phase 2: on first deploy the Hub ensures the Postgres container/role exists on the chosen host, generates credentials into the vault, injects `DATABASE_URL`, registers the per-site nightly `pg_dump | age` → S3/Blob Beat job. Phase 3/4 adds the operator surface (research: even minimal Dokku ships this): browsable backup list, on-demand "test backup now," restore as a documented §6.6-style command block (restore *UI* stays Phase 7), alert-on-backup-failure. The plan's monthly automated restore-test already exceeds all five reference tools — kept. **UPDATE 2026-08-02 (review3 §N6):** §E5 generalizes into a **per-site data-backup registry** — `backup_unit kind ∈ {postgres, sqlite_file, directory_sync}` declared in the manifest; same Beat-job + alert-on-failure + monthly-restore-drill machinery for all kinds; all site-data backups through the same `| age` client-side encryption and off-host key discipline; site-move/adopt flows block or migrate registered volumes.

**E6. Adopt-existing-site playbook (his actual cold start).** The provisioner assumed fresh hosts; Joseph's machines run live manually-managed sites. Adopted: provisioner detects occupied ports 80/443 or non-fresh state and **refuses with an explanation** (one guard clause preventing the worst first-run outcome — taking down production during enrollment); an "Adopt a site" flow in Phase 3: scan project → deploy via Hub to a temp subdomain → verify → migrate/point DB → flip real DNS → decommission old path.

**E7. Non-Django boundary stated + two thin passthroughs:** ① **Has-Dockerfile** projects deploy as-is (generic checks: EXPOSE, health path, non-root, Trivy) — wizard asks only domain/target/env/port; ② **Static folder** — no container; rsync build output to a Caddy static route. Deep readiness analysis stays Django-only, explicitly. ## K. Partner Deploy API & MCP Server (added 2026-07-30; requirement: other platforms trigger auto-deploys)

**Requirement (Joseph):** other websites (partner platforms) whose clients pick a website must be able to call this system — REST API or MCP tools — and have it auto-deploy that site with no human action. This is the first internet-facing, multi-tenant surface in the product; it was designed by a dedicated 3-agent round (MCP-spec research, platform-API research, security review) — sources in §K9.

**K1. Architecture — "public intake, private Hub, one-way pull."** The Hub-isolation invariant survives *literally*: the Hub gains **zero** inbound internet paths. A new, deliberately tiny **Partner Intake** service (a few hundred lines, own $5 cloud VM, tailnet-tagged `tag:intake`) is the only public piece — exposed at `api.partners.<domain>` via Cloudflare Tunnel behind WAF + rate rules. The intake is **credential-free by construction**: it holds partner *public* keys, quota counters, and a job outbox — no SSH keys, no vault/KEK, no Hub Postgres, and **no Celery broker access** (broker write = root fleet-wide, §B4). A Hub Beat job polls the intake's outbox over the mesh every 5–15 s; tailnet ACLs allow Hub→intake:443 and give the intake routes to *nothing*. A fully-compromised intake can therefore only submit well-formed job requests that the Hub independently re-validates — a TeamCity-class auth-bypass in the intake is *survivable by design*. (Rejected: a Cloudflare-proxied `/api/partner/*` namespace on the Hub itself — that puts the crown-jewel process behind internet request parsing, exactly the CVE-2024-27198 failure class; CF proxying filters floods, not auth-logic bugs.)

**K2. Partner auth.** Per-partner **Ed25519 keypairs**: partner signs (method, path, SHA256(body), timestamp, nonce); 5-minute window + replay cache; intake verifies with the public key (cheap edge rejection + quota accounting), the Hub **re-verifies authoritatively** against the vault-held record and re-runs full §4.5 validation — the intake is untrusted input. Two active keys per partner (zero-downtime rotation, 90-day schedule via the §7.4 playbook pattern), instant revocation (Hub immediately; edge instantly via a per-partner Cloudflare Access service token/WAF rule the kill switch disables). HMAC/bearer offered only as a compatibility fallback for partners who can't sign — that secret then lives **Hub-side only**, with auth deferred to the Hub for those partners. Key material discipline: shown once, `hubk_live_`/`hubk_test_` prefixes for leak scanning, hashed/vaulted at rest. **UPDATE 2026-08-02 (review3 §M5):** the **Hub owns the authoritative replay defense** — its own timestamp-freshness check, nonce/replay cache, and idempotency-key store in Postgres; the intake's copies are demoted to cheap edge rejection.

**K3. The API (6 endpoints are enough — industry-converged shapes, invented nothing):** `POST /partner/v1/sites` (template ref, tenant ref, desired subdomain; **Stripe-style `Idempotency-Key`** — first response stored 24 h keyed by key+params-hash, replays return it verbatim, param mismatch = 422) → 201 · `POST /sites/{id}/deployments` → **202 + status polling** (the universal PaaS shape: queued→building→ready|error, reusing the §D2 state machine verbatim; same-commit+config dedupe unless `force`) · `GET /deployments/{id}` · `POST /sites/{id}/domains` → returns the exact CNAME + ownership TXT to show the end client · `GET /domains/{hostname}` (verification + ssl status) · idempotent `DELETE`s (absent = 204). Rate limits per key (Netlify's proven numbers): ~60 req/min general, deploy-create 3/min + 100/day per site, `X-RateLimit-*` headers; per-partner quota columns (max_sites, deploys/day, domains) enforced in the create paths. **Webhooks = Standard Webhooks spec exactly** (`webhook-id`/`webhook-timestamp`/`webhook-signature`, HMAC-SHA256 over `id.timestamp.payload`, `whsec_` secrets, dual-secret rotation) so partners verify with off-the-shelf libraries; delivery is egress-only from the Hub, SSRF-guarded by the §B10 validator, retried ~5× over 24 h, disabled+alerted on sustained failure; polling stays the source of truth.

**K4. Domains & TLS (no new ACME machinery at all).** Auto-issued tenant subdomains: one wildcard `*.apps.<partner-base-domain>` proxied record + wildcard edge cert → a new subdomain is a DB row + Caddy route, zero DNS calls. The partner base domain is **never** a domain hosting Joseph's own prod sites (cookie + reputation isolation). Custom client domains: **Cloudflare for SaaS custom hostnames** — free for the first 100 hostnames, $0.10/mo after, on non-Enterprise plans; TXT **ownership verification before anything is ever served** (an unverified domain would make the fleet a phishing factory on Joseph's IPs and CF account), client CNAMEs to the fallback origin, Cloudflare owns cert issuance + renewal — fully consistent with §B2's no-ACME-tokens-on-targets rule. Slots into the provider layer as a `CustomHostname` capability on the Cloudflare adapter. Lookalike-brand denylist + per-partner domain-claim rate limit.

**K5. Execution & tenancy.** Validated jobs become ordinary Deployments in a new **`tier: partner`** with hard rules: **v1 deploys template-catalog images only** — Joseph-built, digest-pinned, Trivy-gated; partners supply config/content through a constrained schema, never a Dockerfile, never a build step (arbitrary partner-client code is explicitly out of scope for v1; if it ever ships it gets dedicated per-partner or ephemeral hosts, dedicated builders, egress filtering, and its own review).

*Destination policy (updated 2026-07-30 per Joseph — own servers are a supported option):* partner sites deploy to targets from a per-partner **destination order** you configure, choosing among ① dedicated cloud targets (the cautious default — rented blast radius, disposable IPs) and ② **your own servers, enrolled as partner-tier targets** — free capacity you already own, fully supported. The uniform-target principle makes this trivial (a target is a target); what stays non-negotiable are the isolation rules, which apply on *any* destination: a partner-tier target is **dedicated to the partner tier** — never co-hosted with your prod/staging/experiment sites and never the Hub host (§9.6.2 r1/r2); **Cloudflare Tunnel mode required** for own-server partner targets (zero inbound ports, your IP never exposed under someone else's content); own VLAN/zone segmentation advised, with the Topology Advisor flagging amber if a partner-tier box shares a flat LAN with personal devices (r5); per-site Docker networks; mandatory `--memory/--cpus`; excluded from overflow auto-scaling. One honest trade-off surfaced in the UI when you pick an own server: abuse takedowns and IP-reputation damage from a partner's client content land on hardware and residential/office connections you can't dispose of — the wizard states it once and respects your choice. `PartnerSite` rows are FK-bound to their Partner and every queryset filters on it.

**K6. Machine callers can't do step-up — so the API structurally can't reach dangerous actions.** The partner surface is a server-side action allowlist (create/deploy/status/suspend/delete *own* sites in *own* namespace). No route touches targets, vault, keys, tiers, Hub settings, or DNS beyond the partner namespace — and a standing test asserts the partner router maps to no §F5 T1/T2 internal action, so a refactor can't silently widen it. **UPDATE 2026-08-02 (review3 §M5/§V3):** the standing-test list gains: a replayed signed request is rejected at the Hub even when the intake forwards it; job commands on partner-tier sites are prohibited.

**K7. Abuse economics & new threat-model rows.** Three §6.8 additions: *malicious/compromised partner platform* (valid creds, mass provisioning) → scoped keys + quotas + budget caps + tier isolation + kill switch; *partner's fraudulent end-client* (site/content is the attack) → template-only + domain verification + takedown path; *internet attacker vs the intake* → credential-free intake + pull model + CF front. Kill switches at three layers: per-partner suspend (containers stopped, routes detached, key revoked, edge token disabled), global partner-API flag (like `reconcile_enabled`), per-site takedown (route → 410). Abuse contact + SLA published; CSAM/phishing reports = automated immediate suspend. **K8. MCP server — thin adapter, never a second privilege path.** Research-verified stack: **Streamable HTTP, stateless, single POST `/mcp` endpoint** on the intake (the old HTTP+SSE transport is deprecated — don't build it; the brand-new 2026-07-28 stateless spec revision is 2 days old and mid-SDK-churn, so build against 2025-11-25 semantics and pin **`mcp>=1.x,<2`**, migrating to SDK v2 deliberately later). Auth: MCP is spec-legitimate as a plain OAuth-style *resource server* validating bearer credentials — pre-registered credentials are a sanctioned client-registration mode, and pre-provisioned tokens are how production machine clients (including Anthropic's MCP connector) authenticate today; the MCP layer therefore uses **the same partner credential, verification path, quotas, and audit trail as REST** — one revocation, one attack surface. Tools are **curated and task-shaped, never auto-generated from the OpenAPI schema** (documented anti-pattern): `create_site`, `deploy_site`, `get_deployment_status`, `add_custom_domain`, `get_domain_status`, `remove_site` — each a ~10-line wrapper over the same service-layer functions the DRF views call (§D4's service layer is the single home of the logic). Deploys return `deployment_id` immediately; status is polled — matching the REST 202 pattern. Origin-header validation (spec-mandated DNS-rebinding defense) + TLS at the edge. MCP tool inputs are untrusted (prompt injection reaches the partner's LLM); the Hub's serializer validation stays the authoritative gate. OAuth 2.1 discovery (RFC 9728 metadata) is a cheap later add if a partner's client demands it. **UPDATE 2026-08-02 (review3 §U1):** the MCP adapter is **cut from Phase 5.5 v1** — REST-only until a named partner's client demands MCP; the design above is retained for when that happens.
