## M. Security — adopted fixes (priority 1)

**M1. Scan-phase execution moves off the Hub (critical; the round's most serious finding).** *(Modifies scanner addendum §S1/§S4; master plan §5.1; extends 07-30 §B1.)* Two lenses independently confirmed the same hole: §B1 moved `docker build` off the Hub because builds execute arbitrary project code — but the **scan phase itself** still runs on the Hub (§A4: the Hub clones the repo; §5 scans it), and the scan phase executes project code too: `npm run build`/`collectstatic`/"tests exist and pass" in the Django module, and now `pnpm install --frozen-lockfile` (lifecycle/postinstall scripts), `tsc --noEmit` (requires installed node_modules, plugins execute), "production build succeeds," and the S1 common core's "Dockerfile generation + **build verification**" in the node-ts module. B1's own rationale — "a malicious lockfile dependency gets the keys to the fleet" — applies verbatim, and a large pnpm tree (CCXT and friends) is exactly the §6.8 postinstall supply-chain surface. The common core's build-verification check also contradicts B1 structurally: at scan time no deployment target has been chosen, so there is no sanctioned place to build.

Decision — an **execution-placement rule** added to §S1, applying retroactively to the Django module:
- Every scanner check is classified **static** (AST/file/manifest/lockfile reading, gitleaks, `pnpm audit`, detection heuristics — allowed on the Hub) or **executing** (install, build, test-run, collectstatic, `tsc`, docker build). The classification is part of the module interface.
- Executing checks run only in a **disposable, network-restricted, vault-free sandbox off the Hub** — the §A7 `hub-test-target` machinery or the deployment target/builder — with results shipped back as the check report. Never on the Hub, no exceptions.
- The install-verification check runs with `--ignore-scripts` (pnpm 10's default script blocking is noted but **not relied upon**; the flag is explicit).
- "Image builds successfully" is **deleted from the scan phase** and deferred to pipeline step 1, where §B1 already governs it. The scanner's Dockerfile *generation* (pure templating) stays.
- New conformance requirement **SEC-SCAN-NOEXEC** (§Q1) with a T1 test asserting the scanner's Hub-side code path invokes zero subprocess/npm/pip/pnpm entry points.

**M2. Phase-2 webhook deploys are replaced by git polling (high).** *(Modifies 07-30 §E1 and the §I Phase-2 line.)* "One authenticated per-site webhook endpoint" in Phase 2 is impossible without violating the zero-inbound invariant (§K1, R1, the TeamCity lesson): GitHub webhooks originate from the public internet, and the only public surface (Partner Intake) doesn't exist until Phase 5.5 — a dependency scheduled three phases before its prerequisite. Decision: **Phase 2 ships polling** — a Beat job checks each site's branch head every 1–5 min (~30 lines, zero new attack surface, fully consistent with the §A4 pull model; functionally equivalent for a solo operator). True webhooks become a second credential-free **outbox message type on the Phase-5.5 intake** — the Hub pulls them like partner jobs. A standing test asserts no Django URL route is reachable from a non-tailnet source. §E1's research conclusion (push-triggered deploys are the baseline interaction) stands; only the transport changes.

**M3. The pager channel gets authenticated (high).** *(Modifies alert-protocol.md §3/§6; adds a §6.8 threat-model row.)* The ntfy topic name is a bearer token deliberately spread to every fleet server (interim `server-watch.sh`) and to healthchecks.io — so any compromised target can **read** every alert (hostnames, container names, live incident state, via a third-party service), **spoof** alerts including a forged P1 whose "break-glass" line is an attacker-chosen shell command the protocol has trained Joseph to type at 2 a.m., or **flood** the topic until the §4 storm breaker collapses a real alert into an attacker-generated summary. Decisions:
- ntfy access tokens are **mandatory from day one**, not "defense-in-depth" — reserved/protected topics, deny-all default, and a **distinct publish token per server** (and for healthchecks) so one compromised host is identifiable and revocable.
- New §3 rule: **break-glass commands arriving over the pager channel are advisory only** — re-read them from the Hub-served Findings inbox (over Tailscale) before typing; never execute a command whose only provenance is a push notification.
- Push bodies are minimized: object + severity + duration + deep link; host aliases, never raw IPs; full detail lives behind the tailnet. The trade-off (self-sufficient alerts when the Hub is down) is preserved by keeping the break-glass text in the *email* copy, which the §B10 scrubber discipline and this advisory-only rule now cover.
- §6.8 gains an "alerting channel" row recording topic names as vaulted secrets and the spoof/flood/leak attacker.

**M4. Sites gain an exposure mode; broker credentials enter the threat model (high).** *(Adds to master plan §4 Site model, §8 step 6, 07-30 §F3; adds a scanner check to both modules.)* Everything downstream assumes every site is a public Cloudflare-proxied website: Site requires a domain, §8 step 6 has no skip path, F3 makes "connect Cloudflare" a first-run prerequisite — and the node-ts module has no authentication check. The combination **default-publishes the trading HUD** (live P&L, positions, endpoints backed by Alpaca/broker keys that can move real money) to the internet with no auth; the only hint otherwise is one clause in §7.1.0 about internal *targets*. Decisions:
- `Site.exposure ∈ {public, mesh_only}`. `mesh_only` skips DNS/edge steps entirely, binds the Caddy route to the tailscale interface (Tailscale HTTPS certs or plain mesh HTTP), uses mesh-side uptime probes, and the Topology Advisor asserts no public path exists.
- Scanner check (both modules): **no authentication detected on a `public` site = Warning; Blocker** when the wizard tags the site as containing financial/personal data.
- First-run checklist: the Cloudflare step is skippable when the first project is `mesh_only` — the trading service is a plausible *first* deploy.
- §6.8 gains a row for **financial/broker credentials on targets** — a money-moving credential class distinct from generic env vars; the node-ts module surfaces a warning recommending read-only/paper keys where the broker supports scoping.

**M5. Replay defense moves to the Hub (high).** *(Modifies 07-30 §K2/§K3; extends the §K6 standing-test list.)* §K2 placed the 5-minute window + replay cache on the intake while the Hub "re-verifies authoritatively" only signature and schema — but the intake is *modeled as fully compromisable*: it can hold captured, validly-signed partner requests and re-submit them at will (re-triggering a DELETE after the partner recreated the site; rolling a site back to older template config), and K3's idempotency keys live intake-side, so the 24-h dedupe is equally forgeable. Decision: **the Hub owns the authoritative replay defense** — it re-checks timestamp freshness and maintains its own nonce/replay cache and its own idempotency-key store in Postgres (it already stores first responses); the intake's copies are demoted to cheap edge rejection. §K6's standing tests gain: *a replayed signed request is rejected at the Hub even when the intake forwards it.*

## N. Stability — the stateful-site deployment problem (priority 2)

Three lenses independently confirmed the same structural defect, the round's second critical cluster: **the pipeline's only deploy strategy corrupts the trading stack's state, and S1's "everything downstream is untouched" sentence is false.**

**N1. Per-site deploy strategy: `blue_green | recreate` (critical).** *(Modifies scanner addendum §S1/§S4; master plan §8 steps 4–9; 07-30 §D2/§D6/§F4; adds Phase-2 roadmap work.)* S4 states the constraint — "cutover order must stop the old writer before the new one writes; WAL does not make concurrent cross-container writers safe" — but the pipeline it patches structurally violates it: §8 starts green alongside blue (step 4), and green must *complete warm-up backfill*, writing SQLite/Parquet/snapshot state on the shared named volume, to pass step 5 — while blue still serves and writes. DuckDB's exclusive read-write file lock may prevent green from even opening the files. The constraint is unsatisfiable as specified, not merely awkward; the scanner warns while the pipeline executes the unsafe order. Decisions:
- The manifest and §D2 gain **`deploy_strategy: blue_green (default) | recreate`**. Recreate = stop old → start new → wait ready → route, with the downtime window (which includes backfill) stated honestly in the UI, and uptime-probe/`maintenance_until` suppression during the window so the cutover gap doesn't page.
- **Recreate is mandatory** (Blocker if overridden) for sites where the §9.5.6/S4 local-state findings fire; the scanner sets it automatically.
- **Named-volume ownership pinned in §D6:** volumes are per-**Site** (`site-{slug}-data`), never per-deployment; created by an idempotent ensure-step; never touched by rollback, the reaper, or decommission without a T1-tier confirmation.
- The §F4 failure-impact table gains recreate rows (failures mean "site IS down," not "old version still serving"); the §G crash kill-matrix and a T2/T3 test cover the recreate path, asserting the old writer is stopped before the new one opens the DB.
- **S1's "Everything downstream is untouched" sentence is deleted**, replaced by an explicit list of the downstream deltas this module introduces (deploy strategy, volumes, readiness gating, ws-drain tuning, per-site job runtimes). The pipeline work is a named **Phase 2 line item (~3–4 days)** — it was previously scheduled nowhere (§S5 costed only the scanner).

**N2. Liveness / readiness / staleness become three modeled things (critical).** *(Modifies scanner addendum §S4; master plan §4/§6C/§8 step 5; 07-30 §D3; alert-protocol §2 — see O1.)* S4 demands readiness-vs-liveness and data-staleness in `/healthz`, but nothing downstream models them — and worse, the demanded wiring is *wrong*: routing last-tick age into the uptime probe and reconciler means that for a market-data system, **feed silence — the normal state most of the week** (TWSE closes 13:30; US markets close nights and weekends) — would open P1 site-down pages every evening and restart a healthy container whose only fault is a closed market, triggering a full rate-limited backfill and going stale again: a restart loop that risks API bans while fixing nothing. Also unenforceable as written: "Blocker if /healthz returns 200 before the engine is warm" is a runtime property no static scan can decide. Decisions — the contract splits three ways:
- **Liveness** (process up, event loop responsive) is what the uptime probe and reconciler act on. **Readiness** gates traffic cutover only. **Feed-staleness** is a separate metric field producing its own Finding class (see N3) — **explicitly excluded from reconciler restart triggers**.
- Manifest/Site fields added: `liveness_path`, `readiness_path`, `warmup_timeout_s`, `data_staleness_threshold` (per-feed), plus the E9 fallback preserved (§V7).
- A **pinned `/healthz` JSON contract** — `{live, ready, checks: {feed_age_s, backfill_pct, ...}}` — becomes a Phase-1 interface alongside the §C3 collector contract; three consumers (pipeline step 5, uptime prober, reconciler) parse it, so its shape cannot stay implicit.
- **§8 step 5 gates on `ready`**, with per-site `warmup_timeout_s` as a manifest field (wizard asks; node-ts module defaults it high, 10–15 min — the fixed Django-tuned timeout would false-rollback every healthy trading deploy and burn upstream quota on the retry). The readiness endpoint reports progress so the stepper distinguishes "warming, progressing" (wait) from "stuck" (roll back); observed warm-up duration is logged per deploy for data-driven tuning.
- §D3's `observed_state` gains **`unhealthy`** and **`warming`**: `unhealthy` (live but failing) → restart once, then §C2 backoff; `warming` → probes don't count toward down-hysteresis; only "warm-up exceeded budget" alerts (P2). Warming renders on site cards and the fleet view with elapsed/expected time, and joins the §F8 simulation seed so the review loop actually renders it. The scanner's Blocker is downgraded to *pattern detection* (a readiness gate exists in the handler); the enforceable gate lives in the pipeline — registered as two separate conformance reqs (`SCAN-S4-READINESS-PATTERN`, `PIPE-S4-READINESS-GATE`) so the split can't silently collapse.

**N3. Feed-staleness repair policy: alert-first, restart-almost-never (high).** *(Adds one paragraph to §S4; adds alert rows per O1.)* Staleness is evaluated against a **per-feed market calendar or max-expected-gap config**, routed **P2 at most**, and the reconciler policy is pinned: `/healthz` reports per-feed status (`upstream-connected` vs `process-wedged`); data-stale = alert first, restart **at most once**, and **never restart when the feed reports upstream-down** — a restart cannot fix the exchange's own downtime and only destroys the ring buffer and forces a rate-limited re-backfill.

**N4. Exclusive upstream connections (high).** *(Adds to §S4 ingestion checks + wizard.)* During any overlap window two containers run two ingestion daemons against the same upstream accounts: Alpaca's standard plan permits **one concurrent websocket per account** (green never becomes ready, or kicks blue's live feed mid-serving); FinMind quotas can be exhausted by a double backfill. Decision: scanner check + wizard question flagging **exclusive-upstream feeds**; flagged sites require the recreate strategy (N1) or a documented handoff (old instance pauses ingestion via pre-stop hook before green warms). Backfill checks gain rate-limit guidance: bounded concurrency, **resume-from-checkpoint** rather than full re-backfill on restart.

**N5. Volumes enter the data model (medium).** *(Adds to master plan §4 manifest spec; 07-30 §D3/§D6.)* S4's named-volume requirement had no home: no field records a site's volumes, so no ensure step, no machine-readable backup location, no P4 snapshot of mount config — a container recreated without its volume mapping silently starts on an empty data dir, the exact failure the requirement exists to prevent. Decision: the manifest gains a **volumes list** (name, container path, backup policy), a D6-style idempotent `ensure_volume` primitive shared by pipeline and reconciler, and volume presence in the reconciler's observed state.

**N6. Site-data backup lifecycle gets an owner (high).** *(Modifies 07-30 §E5/§G; scanner addendum §S4; alert-protocol §2.)* S4 mandates nightly SQLite `.backup`, Parquet partition sync, and "DuckDB files copied cold" — but every existing backup/restore mechanism is Postgres-shaped, so the new class had no registering model, no restore drill, no failure alert, no encryption statement, and the Topology Advisor's "move site to another target" would silently strand host-disk state. Also, "copied cold" is impossible for a 24/7 daemon, and 24/7 tick ingestion fills the disk on a predictable curve §C7 doesn't cover. Decisions — §E5 generalizes into a **per-site data-backup registry**:
- `backup_unit kind ∈ {postgres, sqlite_file, directory_sync}` declared in the manifest; the same Beat-job + alert-on-failure + monthly-restore-drill machinery covers all kinds; site-move/adopt flows block or migrate registered volumes.
- All site-data backups go through the same **`| age` client-side encryption** and off-host key discipline as §E5 DB dumps (the §6.9 "stolen backups are useless" invariant applies to this site class too).
- **DuckDB is documented as derived data, rebuildable from Parquet — excluded from backup** (replacing "copied cold"); Parquet sync is **incremental (new partitions only)**, with backup size/duration in the P3 digest against the ~$5/mo posture.
- Local Parquet partitions are **pruned after successful object-storage sync** beyond N days, and the node-ts checks add a **days-to-full disk forecast** finding so the operator acts before the 85 %/95 % thresholds.
- Non-Django sites gain a **generic pre-cutover migrate hook** in the manifest (a container command), plus a scanner warning on rollback-across-schema-change — §D6's migrate step was Django-only, so nothing guarded SQLite schema changes against rollback landing old code on a newer schema.

**N7. The Python offline component gets a mechanism (high).** *(Modifies scanner addendum §S4; 07-30 §E8; corrects the §12.4 citation to §E8.)* S4 routes backtesting to the scheduled-jobs UI, but §E8's mechanism — cron `docker exec` into the site's container — **cannot run it**: the production image is Node-only; vectorbt/Polars/Python 3.12 exist in no image anyone builds. The single stated home for backtest runs was a dead end. Decision (made now because it's a schema question Phase-2 tables will freeze): **v1 ships backtesting as manual-only, stated plainly in the wizard** — but the manifest schema gains a nullable second image reference (`jobs_image`) *now*, and §E8 gains a second job type in Phase 3: **"run image X with volume mounts Y"** — a per-job container built by the common-core Dockerfile machinery from the `pyproject.toml` the scanner already detects, sharing the site's Parquet volume read-only, same §B1 build rules, same Trivy gate, each run logged in the existing per-run surface with failures classified per O1.

**N8. Per-site deploy policy: don't restart the engine mid-session (high).** *(Adds to 07-30 §E1/§D2 and the node-ts wizard.)* Nothing prevents an automatic deploy from severing every live ws client and cold-starting a multi-minute backfill while the market is open; `maintenance_until` pauses the reconciler, not deploys. Decision: per-site **`deploy_policy: auto | confirm | windowed (cron expression)`** — polling/webhook-triggered and reconciler-triggered image changes queue outside the window and fire a P3/P2 "deploy waiting" notice; manual deploys inside a blocked window show a T2-confirm warning. Small model + one pipeline guard; the node-ts wizard asks.

## O. Observability & alerting — adopted fixes

**O1. The rules table absorbs the new alert classes (high).** *(Modifies alert-protocol.md §2 — honoring its own "classified before it ships" rule, which the 08-02 addendum and §K5 both violated.)* New rows:
- **Feed data-stale beyond per-feed threshold (market-calendar-aware) = P2 push** — arguably the single alert Joseph most wants from this project; never a restart trigger (N3).
- **Instance warm-up exceeded budget = P2**, escalating P1 only if no ready instance is serving.
- **Scheduled app job failed = P2 with consecutive-failure hysteresis**; individual run failures P3 digest.
- **Partner-tier site hard-down = P2 by default** (not the prod-P1 row, not the staging row — it was in neither), escalating to P1 only on aggregate signals: N partner sites down simultaneously, or a partner-tier target host down. Correspondingly, **§K7's published SLA is restated as response-time, not uptime** — a solo operator cannot staff a wake-me SLA for other people's end clients, and the published text must match what the rules table actually delivers.
- **Intake unreachable > 5 min = P1** (partner-facing platform down); **Hub→outbox poll failing N cycles = P2**; **target cron job failed/stale = P2** (interim: both delivered cron scripts curl the ntfy P2 topic on failure — two lines each — so `update-cloudflare-ufw.sh` going stale can't silently rot toward blocked users).

**O2. The Partner Intake becomes a first-class operational citizen (high).** *(Modifies 07-30 §K1/§K9; server-hardening.md; build-process.md.)* The product's only internet-facing surface was outside every loop: no uptime probe, no HostMetric, no hardening profile ("two firewall postures, never one" — the intake is neither), no upgrade owner, no CI, and `intake/` missing from the sensitive-path list even though its K9 stubs land in Phases 0–3. If the intake dies, partner deploys silently stop and Joseph learns from an annoyed partner — the exact watcher-class gap §C5 closed for the Hub. Decisions: the intake VM is **enrolled as a Target** (provisioned by the §7.1 playbook, new hardening profile `intake` = tailnet member + Tunnel-published service, verified by the same scripts, probed externally via `api.partners.<domain>`); its **upgrade path is defined in §K9** — the natural answer is the Hub deploys it as a mesh-managed internal site (dogfooding), with a `hub-upgrade.sh`-style script as the pre-Phase-5.5 fallback; **`intake/**` joins the §5 sensitive-path glob now** and gets its own on-push CI lane; alert rows per O1.

**O3. WebSocket-class sites get honest dashboards (low, adopted).** *(Modifies master plan §9 card spec; extends the §C3 collector JSON contract by one field.)* All health/traffic visuals derive from Caddy HTTP access logs; a ws-push service emits ~one line per connection upgrade, so its card reads as a dead flatline while healthy and shows nothing when degraded. Decision: for ws-class sites (the scanner already detects `ws`), the card's primary metric becomes **last-tick age + active connection count** from the /healthz contract the collector already fetches — a rendering rule, not new machinery.

## Q. Plan-conformance verification system (priority 4 — Joseph's 計畫-成品一致性 requirement)

The root gap: nothing machine-checkable connects the plan docs to the code. `REVIEW_CHECKLIST.md` is derived from the plan *by hand*; a requirement with no test, a plan section silently unimplemented, or an addendum landing after its phase already exited (**exactly what the 08-02 addendum did to Phase 1's specified scope**) is undetectable. The existing mechanisms (checklist, §2-④ doc-sync exit gate, Scribe role) are real but manual and unverified. This section assembles the quality lens's design into one spec. It patches `build-process.md` §2/§3/§4/§5/§7.

**Q1. The requirements registry — `conformance/requirements.yaml`.** One entry per testable plan invariant, schema-validated in CI (`conformance/schema.json`):

- `id` — stable, domain-prefixed slug (`SEC-B1-BUILD-OFFHUB`, `REL-C2-BACKOFF`, `PART-K2-REPLAY`, `SCAN-S4-READINESS-PATTERN`, `PIPE-S4-READINESS-GATE`, `PROC-REGRESSION-TEST`, `ALERT-P1-ROWS`, `HARD-R3-IGNOREIP`, …)
- `source` — doc#section anchor (e.g. `plan-addendum-2026-07-30.md#B1`)
- `statement` — one normalized sentence
- `kind` — `invariant | behavior | interface | process`
- `phase` — the phase whose exit requires it
- `verify` — `test | checklist | demo | static-gate`
- `status` — `planned | implemented | verified | retired` (retired entries keep their id + reason forever; never deleted)

Seeded in **one extraction pass** over the already-enumerated invariants (§1.5 P1–P5, §B1–B10, §C1–C7, §D1–D9, §E1–E10, §F1–F9, §K1–K8, §S1–S5, this addendum's §M–§O, the alert-protocol rules table, hardening R1–R10) — the stable §-IDs make this ~1–2 days of agent work plus a Joseph skim, ~150–250 entries. The registry **joins the §5 sensitive-path list** and inherits the §4 anti-gaming rule verbatim: it is never edited in the round being judged by it.

**Q2. Enforcement — the red/green link requirement→test→CI.** Traceability lives **in the tests**, not a separate matrix file (separate matrices drift): every test claiming a requirement carries `@pytest.mark.req("SEC-B1-BUILD-OFFHUB")`; module-level mappings live in `conformance/paths.yaml` (module glob → req ids). One new per-push CI job, `conformance-check` (~150-line `conformance/check.py`, no external tooling), asserts: **(a)** every registry entry with `verify: test` and `phase ≤ current` has ≥ 1 collected test bearing its marker — else red; **(b)** every marker in the suite resolves to a live registry id — unknown or retired id is red (catches renames and deletions); **(c)** emits `conformance/matrix.json` (req → test ids → last status) as a build artifact. The **phase exit gate** (§2-④) adds `check.py --phase N`: every phase≤N req is `verified` (its tests green in the gating CI run) or has a `WAIVERS.md` line; a `verify: demo` req requires a checked-in record under `conformance/demos/phase-N.md`. "A requirement with no linked test = red" becomes literal. *(Adopted from a downgraded finding — the verifiers correctly noted this is an enforcement design, not a defect per se; it rides Q1's registry, which is the defect.)*

**Q3. Spec-drift detection, both directions.** *(Adopted from a downgraded finding; the verifiers correctly noted the checklist/Scribe/exit-gate mechanisms exist — this makes them mechanical.)* **Plan→code:** the repo carries the frozen build copy of the plan docs at `docs/plan/*.md` (the agents build from the repo anyway; the Scribe syncs Project↔repo at phase exit; a nightly job diffs the two and files a P3 finding on divergence). Each registry entry stores `text_hash` = sha256 of its source section body; `conformance-check` recomputes them — a section changed while its reqs' hashes are stale = red, forcing the same PR that edits a doc to touch the registry, and the check prints the linked test ids as a "re-review these" list that persists as a standing round finding (fingerprint = req id) until resolved. **Code→plan:** on every PR, a CI job maps `git diff --name-only` through `paths.yaml` and writes "this diff is governed by §B1, §D6 (reqs: …)" to the job summary — reviewer agents see exactly which plan sections a diff is answerable to, with zero bot infrastructure.

**Q4. Executable phase acceptance.** Phase milestones were prose; "the demo is a test" had no derived artifact, and Phases 0/1/5.5 had no executable form at all. Each phase gains `tests/acceptance/test_phase_N.py` — each test a literal transcription of one milestone clause, marked `@pytest.mark.acceptance(phase=N)` and carrying the reqs it proves; runs in whichever tier fits (Phase 0–1 per-push; Phase 2+ rides nightly T3). Milestones needing private/real resources split: the CI-runnable half targets the fixture (Q7), the real-world half is a `verify: demo` req recorded in `conformance/demos/` with actual output attached (e.g. the real trading-repo readiness report). The Adversarial verifier's §2-④ sign-off **explicitly re-runs the acceptance module from a clean checkout** — its "re-derives the exit claims" mandate becomes a command instead of judgment.

**Q5. One finding queue — the rounds consume the registry.** `make review-round` gains **step 2.5:** run `conformance-check`; its three outputs (uncovered reqs, stale reqs, phase-gate misses) are injected into the round's finding queue with fingerprint = req id + state — same triage rule as every finding (fix-with-regression-test or `WAIVERS.md` line; no silent dismissal), persisting across rounds until resolved. `REVIEW_CHECKLIST.md` becomes **partially generated**: every checklist item restating a plan invariant carries its req id inline, and a check asserts every such id is live — replacing hand-derivation with a mechanical, versioned one that catches checklist rot when reqs retire. Reviewer agents receive `matrix.json` in round context, so "is this invariant actually tested" is a lookup.

**Q6.
