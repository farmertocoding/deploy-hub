**Trigger:** Joseph confirmed a second concrete project the Hub must "auto-understand" — a real-time trading/S-R analysis system on a Node/TS stack. The scanner was spec'd Django+React-only; this addendum makes the scanner **modular** and specifies the first non-Django module.

## S1. The scanner becomes modular

§5.1's Detection step is promoted from a paragraph to the dispatch layer: detection identifies the project's shape(s), then runs the matching **scanner module(s)**. Modules as of this addendum: `django` (the existing §5.1 list, unchanged) and `node-ts` (this doc). One project may match several modules — the reference stack below is exactly that (a Node service + a Python offline component + a static frontend in one monorepo), so modules compose rather than compete.

Framework-agnostic checks factor out into a **common core** every module inherits: secrets/gitleaks scan, lockfile pinned, `.gitignore` sanity, tests-exist advisory, Dockerfile generation + build verification, digest-pinned base images (§6.8), and the mandatory `/healthz`. The module interface is `detect() → checks[] → wizard_questions[] → dockerfile_template` — designed for two consumers from day one so a third framework (FastAPI, static site, Next.js) is an add, not a rework.

**REVISED 2026-08-02 (review3):** The sentence "Everything downstream is untouched" (and its supporting clause claiming pipeline, provisioner, DNS/TLS, monitoring, and security suite know nothing about Node vs Django) is **deleted — it was false**. This module DOES force downstream deltas, per review3 §N1: per-site `deploy_strategy: blue_green | recreate`, per-**Site** named volumes, readiness-gated cutover, ws-drain grace tuning, per-site job runtimes (`jobs_image`), and deploy_policy windows. This pipeline work is scheduled as **named Phase-2 line items (~3–4 days)** — it was previously scheduled nowhere (§S5 costed only the scanner).

**REVISED 2026-08-02 (review3, §M1 — execution-placement rule):** Every scanner check is classified **static** (AST/file/manifest/lockfile reading, gitleaks, `pnpm audit`, detection heuristics — allowed on the Hub) or **executing** (install, build, test-run, collectstatic, `tsc`, docker build). Executing checks run only in a **disposable, network-restricted, vault-free sandbox off the Hub** — never on the Hub, no exceptions. The install-verification check runs with `--ignore-scripts`. "Image builds successfully" is **deleted from the scan phase** and deferred to pipeline step 1, where §B1 already governs it; the scanner's Dockerfile *generation* (pure templating) stays. The static/executing classification is **part of the module interface**, applied retroactively to the `django` module.

**REVISED 2026-08-02 (review3, §V7):** The common core's health endpoint requirement follows **§E9 including its fallback** (existing-200-route or TCP probe); the `node-ts` module upgrades it to a hard requirement with readiness semantics (see §S4).

## S2. Reference stack (Joseph's trading project — what `node-ts` must understand)

Node 22 LTS + TypeScript (strict), pnpm monorepo, Bun for dev tooling/tests · Fastify + native `ws` (HTTP for history, WebSocket push for live level/P&L) · ingestion via CCXT websockets (keyless Binance primary), Alpaca (US), FinMind/TWSE (Taiwan), normalized to one Zod-validated `Bar`/`Tick` schema · in-process incremental S/R engine over `Float64Array` ring buffers, worker_threads + SharedArrayBuffer · frontend: TradingView Lightweight Charts v5, HUD-style Bootstrap UI · offline backtesting: Python 3.12 + vectorbt/Numba + Polars/DuckDB reading the same Parquet · storage: partitioned Parquet + DuckDB (no DB server), SQLite (WAL) for app state, append-only level-snapshot store · Rust/GPU deferred behind a `device: "cpu" | "cuda"` seam.

## S3. Detection rules

`pnpm-workspace.yaml` → pnpm monorepo (record workspace packages); `package.json` `engines.node` → runtime version; `tsconfig.json` `strict` flag; deps recognized: fastify, ws, zod, ccxt (→ ingestion-daemon checks fire); source scan for `worker_threads`/`SharedArrayBuffer` usage; `pyproject.toml`/`requirements` with vectorbt/polars/duckdb → Python offline component present; data-path heuristics (`*.parquet` partitions, `*.duckdb`, `*.sqlite3`/WAL files) → local-state findings fire. **Wizard additions:** which workspace package is the deployable service (default from `main`/`bin`/heuristic, confirmed by you); which packages are dev-only; where the data directory lives; expected worker-thread count (analog of the gunicorn-workers question).

## S4. Production checks — the `node-ts` equivalent of §5.1's Django list

**Build & runtime.** `tsc --noEmit` clean under strict; production build succeeds; prod runs compiled JS — `ts-node`/`tsx` in the runtime path is a warning. `engines` pinned to Node 22 LTS and the generated image uses that exact line. `pnpm install --frozen-lockfile` succeeds (the CI-honesty check). **Bun is dev-only:** flagged if any runtime code path requires it — the production image contains Node only.

**Dockerfile generation.** Multi-stage: `pnpm fetch` → build → `pnpm deploy --prod` pruned artifact for the chosen package → slim runtime stage, non-root, `NODE_ENV=production`, digest-pinned base.

**Config & secrets.** All config env-driven; Alpaca/FinMind keys via env, never committed (entropy scan per §4.5); `.env` excluded from image and git. Keyless Binance endpoints noted as no-secret — but rate-limit handling checked instead (see ingestion).

**Fastify serving.** Binds `0.0.0.0:$PORT`; `trustProxy` set (it lives behind Caddy — the Node analog of Django's `SECURE_PROXY_SSL_HEADER`); body-size limits and timeouts set; graceful shutdown on SIGTERM (close the ws server, drain in-flight) — required for blue-green to be clean.

**WebSocket specifics (new check class, no Django analog).** Caddy proxies upgrades natively, but a blue-green cutover severs every live socket: scanner checks for server heartbeat (ping/pong) and advises client auto-reconnect with **snapshot-then-stream** on reconnect — the same pattern the Hub itself standardizes in §3.5, and the scanner says so. Pipeline note: the §8 step-9 grace period is tuned per-site for ws drain.

**Warm-up / readiness (critical for this project).** The ring-buffer S/R engine is meaningless until history backfill completes — so `/healthz` must distinguish **liveness from readiness** and report ready only after backfill, or blue-green switches traffic to a cold instance that answers with empty levels. Blocker-tier if `/healthz` returns 200 before the engine is warm.

**REVISED 2026-08-02 (review3, §N2/§N3):** The contract splits **three ways**: **Liveness** (process up, event loop responsive) is what the uptime probe and reconciler act on. **Readiness** gates traffic cutover only. **Feed-staleness** is a separate metric with its own Finding class — evaluated against a per-feed **market calendar or max-expected-gap config**, routed P2 at most, and **NEVER a reconciler restart trigger** (feed silence is the normal state most of the week; restarting a healthy container for a closed market forces a rate-limited re-backfill and fixes nothing). Restart policy: data-stale = alert first, restart **at most once**, and **never restart when the feed reports upstream-down**. A **pinned `/healthz` JSON contract** — `{live, ready, checks: {feed_age_s, backfill_pct, ...}}` — becomes a **Phase-1 interface**; the manifest gains `liveness_path`, `readiness_path`, `warmup_timeout_s`, and `data_staleness_threshold` (per-feed). §8 step 5 gates on `ready` with per-site `warmup_timeout_s` (the `node-ts` module defaults it high, **10–15 min**). The scanner's "Blocker" above is downgraded to **pattern detection** — a readiness gate exists in the handler (`SCAN-S4-READINESS-PATTERN`) — while the enforceable gate lives in the pipeline (`PIPE-S4-READINESS-GATE`).

**Ingestion daemon.** CCXT/Alpaca upstream streams are background loops, not request handlers — a dead feed doesn't fail any HTTP check. Scanner requires: reconnect-with-backoff on upstream ws; **data-staleness surfaced in `/healthz`** (last-tick age) so the Hub's uptime probe and P1 reconciler catch a silently-frozen feed. This is the single most valuable check for this stack.

**REVISED 2026-08-02 (review3, §N2/§N3):** The wiring demanded above — routing last-tick age into the uptime probe and reconciler — is **superseded** by the three-way contract split: staleness produces its own Finding class per the paragraph above, never a P1 site-down page or a reconciler restart. `/healthz` reports per-feed status (`upstream-connected` vs `process-wedged`) so the repair policy can distinguish exchange downtime from a wedged process.

**REVISED 2026-08-02 (review3, §N4 — exclusive upstream connections):** During any overlap window two containers run two ingestion daemons against the same upstream accounts: Alpaca's standard plan permits **one concurrent websocket per account** (green never becomes ready, or kicks blue's live feed mid-serving); FinMind quotas can be exhausted by a double backfill. The scanner adds a check + wizard question flagging **exclusive-upstream feeds**; flagged sites require the **recreate strategy** or a **documented ingestion-handoff pre-stop hook** (old instance pauses ingestion before green warms). Backfill checks gain rate-limit guidance: **bounded concurrency + resume-from-checkpoint** rather than full re-backfill on restart.

**Workers.** worker_threads + SharedArrayBuffer run fine in Docker, no special flags (COOP/COEP headers are a browser-SAB concern, not server-side); wizard's thread-count answer feeds container CPU guidance.

**State & scale-readiness — the honest finding.** SQLite + local Parquet/DuckDB + the append-only snapshot store = state on host disk → the site is **single-instance only** per §9.5.6 (marked, not blocked — correct for v1 of this project). Consequences enforced: data directory must be a **named volume** surviving container replacement, never image layers; **SQLite multi-writer warning** — blue-green briefly runs two containers, so cutover order must stop the old writer before the new one writes (WAL does not make concurrent cross-container writers safe).

**REVISED 2026-08-02 (review3, §N6):** The backup sentences ("nightly SQLite `.backup` + Parquet partition sync to object storage, DuckDB files copied cold") are replaced. Site data joins a **per-site data-backup registry** — `backup_unit kind ∈ {postgres, sqlite_file, directory_sync}` declared in the manifest, covered by the **same Beat-job + alert-on-failure + monthly-restore-drill machinery** as Postgres, with all site-data backups going through the same **`| age` client-side encryption** and off-host key discipline. **DuckDB is documented as derived data, rebuildable from Parquet — excluded from backup** (this replaces "copied cold", which is impossible for a 24/7 daemon). Parquet sync is **incremental (new partitions only)**; local Parquet partitions are **pruned after successful object-storage sync** beyond N days, and the checks add a **days-to-full disk forecast** finding. The manifest also gains a **generic pre-cutover migrate hook** (a container command), plus a scanner **warning on rollback-across-schema-change** — nothing else guards SQLite schema changes against rollback landing old code on a newer schema.

**Python offline component.** Backtesting is not a serving process: not deployed as a site. Offered as a per-site **scheduled job** or left manual; if it runs off-box it needs a stated path to the same Parquet data.

**REVISED 2026-08-02 (review3, §N7):** The scheduled-jobs UI cited here is the **07-30 addendum §E8** (the earlier §12.4 citation was wrong) — and §E8's mechanism (cron `docker exec` into the site's container) **cannot run backtests**: the production image is Node-only. Decision: **v1 ships backtesting as manual-only, stated plainly in the wizard**. The manifest schema gains a nullable second image reference (**`jobs_image`**) **now** (it's a schema question Phase-2 tables will freeze), and §E8 gains a second job type in **Phase 3**: **"run image X with volume mounts Y"** — a per-job container built by the common-core Dockerfile machinery from the `pyproject.toml` the scanner already detects, sharing the site's Parquet volume **read-only**, same §B1 build rules, same Trivy gate, each run logged in the existing per-run surface with failures classified per review3 §O1.

**Frontend.** Static build served same-origin via Caddy static route; API/ws base URL env-driven; `wss://` in prod verified in the smoke test.

**Audits.** `pnpm audit` replaces `npm audit`; pinned deps; Trivy image gate unchanged.
